## Architecture & Code Quality Review

### Critical Issues

-   **Duplicate Scheme struct definitions:** The `Scheme` struct is defined in both `pkg/store/store.go` and implicitly in `pkg/nav/nav_report.go`. This creates tight coupling and requires manual conversion (`navSchemeToStoreScheme`). 
    - **Solution:** Define a single canonical `Scheme` model in a shared package (e.g., `pkg/models/`) and use it everywhere.
    - Files affected: pkg/store/store.go, pkg/store/memory.go, pkg/nav/nav_report.go, pkg/db/db.go

-   **Inconsistent context usage:** Handlers create new `context.Background()` instead of using `r.Context()` from the HTTP request. This breaks context propagation for cancellation and tracing.
    - **Solution:** Always use `r.Context()` in HTTP handlers.
    - File affected: pkg/api/handlers.go (all 4 handlers)

-   **Unsafe SQL query construction:** `GetUniqueValues` in pkg/db/db.go uses `fmt.Sprintf` to build SQL queries with user input (column name), creating potential SQL injection vulnerability.
    - **Solution:** Whitelist allowed column names or use a map to validate inputs.
    - File affected: pkg/db/db.go:158

-   **Missing error handling for JSON encoding:** All handlers ignore errors from `json.NewEncoder(w).Encode()`. If encoding fails, the client receives partial/corrupted JSON.
    - **Solution:** Check and handle encoding errors properly.
    - File affected: pkg/api/handlers.go (lines 20, 46, 66, 97)

### Architecture Issues

-   **Tight coupling between layers:** The `nav` package contains both parsing logic AND domain models. The `store` package duplicates these models. This violates separation of concerns.
    - **Solution:** Create a `pkg/models/` package for shared domain types. Keep `pkg/nav/` for parsing only.

-   **No dependency injection:** The `Server` struct directly depends on concrete `Store` interface, but initialization happens in main.go with conditional logic. This makes testing difficult.
    - **Solution:** Already using interface pattern correctly, but consider adding a factory pattern or config-based initialization.

-   **Mixed responsibilities in cmd/server/main.go:** The main function handles configuration, database setup, data loading, server initialization, AND signal handling (78 lines). This is too much for a single function.
    - **Solution:** Extract initialization logic into separate functions or an `app` package.
    - File affected: cmd/server/main.go

-   **Inconsistent error handling patterns:** Some functions return errors, some log.Fatal, some do both. This makes error handling unpredictable.
    - **Solution:** Establish consistent error handling: return errors from functions, handle them in main.
    - Files affected: cmd/server/main.go, cmd/fetch/main.go, pkg/conf/config.go

### Redundant/Unused Code

-   **Duplicate cache headers:** All handlers set identical cache-control headers. This should be middleware.
    - **Solution:** Create a `noCacheMiddleware` and apply it once.
    - File affected: pkg/api/handlers.go

-   **Unused context parameters:** Many store methods accept `context.Context` but don't use it (e.g., `MemoryStore` methods).
    - **Solution:** Either use context for cancellation checks or document why it's there (future-proofing).
    - File affected: pkg/store/memory.go

-   **Redundant conversion function:** `navSchemeToStoreScheme` manually copies 15 fields. This is error-prone and will break if fields are added.
    - **Solution:** Use a single shared struct or implement proper mapping with reflection/code generation.
    - File affected: pkg/store/memory.go:103

-   **Duplicate filter logic:** Both `MemoryStore.SearchSchemes` and `DB.SearchSchemes` implement the same filter matching logic differently.
    - **Solution:** Extract common filter logic into a shared function or use a query builder pattern.
    - Files affected: pkg/store/memory.go:48, pkg/db/db.go:108

### Maintainability Issues

-   **Magic strings for column names:** Column names like "fund_type", "fund_strategy" are hardcoded strings scattered across multiple files. Changes require updates in 5+ places.
    - **Solution:** Define constants in a shared package: `const (ColumnFundType = "fund_type", ...)`
    - Files affected: pkg/store/memory.go, pkg/db/db.go, pkg/api/handlers.go

-   **No validation layer:** API handlers directly pass query parameters to store methods without validation. Invalid inputs could cause panics or unexpected behavior.
    - **Solution:** Add input validation middleware or validation functions.
    - File affected: pkg/api/handlers.go

-   **Hardcoded filter columns:** The list of filterable columns is hardcoded in multiple places (handlers, store methods). Adding a new filter requires changes in 4+ files.
    - **Solution:** Define filter schema in one place, generate handlers/queries from it.
    - Files affected: pkg/api/handlers.go:57, pkg/store/memory.go:70, pkg/db/db.go:108

-   **No database migration strategy:** Schema is created with `CREATE TABLE IF NOT EXISTS` but there's no way to handle schema changes/migrations.
    - **Solution:** Add a migration system (e.g., golang-migrate) or version tracking.
    - File affected: pkg/db/db.go:32

-   **Inconsistent naming:** Mix of `NAV`, `Nav`, `nav` in different contexts. `NAVReport` vs `nav_report.go` vs `handleNAV`.
    - **Solution:** Establish naming conventions: use `NAV` for acronyms in types, `nav` for packages/files.

-   **Large converter function:** `appendToParquet` in pkg/fetcher/converter.go is 208 lines with complex logic for reading, building, and writing. Hard to test and maintain.
    - **Solution:** Split into smaller functions: `readExistingData()`, `buildRecord()`, `writeToFile()`.
    - File affected: pkg/fetcher/converter.go

### Performance Concerns

-   **N+1 query pattern in MemoryStore:** Every operation iterates through all strategies → fundHouses → schemes. For large datasets, this is O(n³).
    - **Solution:** Build indexes on initialization (map[code]*Scheme, map[filter][]Scheme).
    - File affected: pkg/store/memory.go

-   **Unbounded result sets:** `GetAllSchemes` and `SearchSchemes` return all matching results without pagination. Could cause OOM with large datasets.
    - **Solution:** Add pagination support (limit/offset or cursor-based).
    - Files affected: pkg/store/store.go, pkg/api/handlers.go

-   **No connection pooling configuration:** Database connection pool uses defaults. May not be optimal for production.
    - **Solution:** Add configuration for max open/idle connections.
    - File affected: pkg/db/db.go
